# Вики разработки — конституция

> **Status**: canon
> **Last updated**: 2026-07-19

Правила ведения знания о разработке English Memory Trainer. Паттерны заимствованы из вики закрытого проекта и **сознательно упрощены** под масштаб проекта (один автор + AI, код ещё не написан). Что именно не переняли и когда пересмотреть — в конце файла.

Не путать с learner-памятью: `memory/` (будущая Obsidian-проекция состояния ученика) генерится движком и руками не редактируется. Эта вики — про **разработку** приложения.

---

## Зоны репозитория

```text
docs/       ← первоисточники: бриф и build-prompt (заморожены, источник для майнинга)
            + design-direction.md (действующая концепция v0.2)
wiki/       ← канон разработки: спеки, глоссарий, roadmap, OPEN
staging/    ← inbox: журналы сессий (append-only), НЕ канон
memory/     ← (будущее) generated learner-память приложения — не часть вики
```

Приоритет источников: принятая спека в `wiki/` (в своей области) → `docs/design-direction.md` → бриф → build-prompt. Спеки пишутся по мере работы и постепенно замещают docs/ как рабочая истина; docs/ не редактируются задним числом.

---

## Принцип 1 — зоны знания не смешивать

Три вида знания, три места:

| Знание | Вопрос | Где |
|---|---|---|
| **Спеки** (target) | что должно быть | `wiki/product/` `platform/` `flows/` `modules/` `glossary.md` |
| **План** | что дальше, что не решено | `wiki/roadmap.md` + `wiki/OPEN.md` |
| **Проверка** | что реально происходит | тесты и findings (появятся с кодом) |

Не вливать баги и код-факты в прозу спек: спека остаётся чистым намерением, реальность сравнивается с ней снаружи. Код-факт в спеке — только со ссылкой на код (`файл.py::символ`), не из памяти. Отдельной генерации REALITY-слоя нет — код сам себе источник; если появится дрейф, добавим чекер.

## Принцип 2 — ось = модуль

Один модуль = одна спека `wiki/modules/<name>.md` (по шаблону [[modules/_TEMPLATE]]). Вся правда о модуле читается в одном файле сверху вниз, без прыжков. Модули — те же, что в коде: curriculum, assessments, evidence, scoring, scheduler, gates, lessons, learner, memory, audit, storage, adapters, cli.

Что не модуль, а `platform/`: сквозная инфраструктура без собственной бизнес-логики (kernel: typed IDs, Clock, envelopes, outbox, Unit of Work, policy registry). Правило-различитель: есть собственные бизнес-правила → модуль; техническая инфраструктура поверх ≥2 модулей → platform. `platform/` держим тонким.

## Принцип 3 — определяем один раз, описываем полностью

- **Словарь** (термины, сущности, состояния, названия score) определяется в одном месте — [[glossary]]. Везде используется по имени.
- **Поведение** описывается полностью inline в спеке модуля. Никаких «см. другой файл» для правил модуля.

## Принцип 4 — спека = target, фазы тегами

Спека описывает финальное состояние. Фаза помечается тегом на элементе: `[mvp]` / `[post-mvp]`. Линия «где мы сейчас» живёт только в [[roadmap]] — статусы в спеки не копируются. Где MVP упрощает target — оба состояния описываются inline рядом.

## Принцип 5 — flow-first

Межмодульные правила выводятся из сквозных сценариев (`wiki/flows/`): «начать сессию → разговор с подмешанными повторениями → зафиксировать evidence → завершить», «placement», «продолжение сессии другим агентом». Порядок написания спек: product → platform → flows → modules. Flow не владеет поведением — полное правило живёт в спеке модуля, flow его выводит и ссылается.

## Принцип 6 — staging ≠ canon, развилки решает человек

- Саммари разговоров и решений пишутся в `staging/journal/` (append-only, институциональная память). Journal никогда не является источником истины — только provenance.
- В канон `wiki/` пишет автор осознанно: концепт → «ок» человека → пишем. При неясности — спросить, не додумывать.
- Продуктовую развилку AI не решает сам: решение принимает человек и помечается `[PD-YYYY-MM-DD]` в спеке и журнале.
- Нерешённое — в [[OPEN]] (единый реестр). Любой OPEN, упомянутый в спеке, обязан иметь строку в OPEN.md.

## Принцип 7 — roadmap простой и ручной

[[roadmap]] — один файл: фазы → work items со статусами (`planned / next / in-progress / done / blocked`) и зависимостями прозой. Правится руками при каждом существенном сдвиге. Без DAG, claims и исполняемых датасетов — пока работает один человек, этого достаточно.

## Правила ведения

1. Каждый канон-файл имеет header `> **Status**` + `> **Last updated**` и секцию «История изменений» внизу (дата + что + почему). `Last updated` бампается при содержательной правке.
2. Новый термин/сущность/состояние сначала вводится в [[glossary]], потом используется по имени.
3. Никаких фактов о коде из головы — только чтение кода или ссылка `файл.py::символ`.
4. Запрещены слова-уклонения в MUST-зонах спек: «TODO», «как-нибудь», «при необходимости», «потом решим». Либо правило, либо честный OPEN.
5. Mermaid для диаграмм: context map (`flowchart`) в platform, сценарии (`sequenceDiagram`) во flows, lifecycle (`stateDiagram`) внутри спеки модуля.
6. Вики читается и линкуется в Obsidian (`[[...]]`), репозиторий уже открыт как vault.

## Что сознательно НЕ переняли из закрытого проекта

| Механизм | Почему не сейчас | Когда пересмотреть |
|---|---|---|
| Norm-registry, norm_hash, machine rules | нет кода, который проверять; тяжесть не окупается | первый пойманный дрейф спека↔код |
| Механические гейты (`check_wiki_spec`, pre-commit) | правил мало, соблюдаются вручную | рост числа спек > ~10 или повторные нарушения |
| Executable roadmap (DAG, claims, leases) | один участник, конфликтов файлов нет | второй участник или параллельные agent-сессии |
| Intake-ledgers, red-team ревью спек | объём знания пока мал | спеки модулей перед началом реализации kernel |
| Workflow-acceptance (E2E против journeys) | нет UI/workflow | появление рабочего CLI-флоу урока |

Принцип из закрытого проекта «правило без гейта = не введено» здесь ослаблен честно: правила держим настолько простыми, чтобы их можно было соблюдать без линтера.

## Структура

```text
wiki/
├── README.md          ← этот файл (конституция)
├── glossary.md        ← термины, определены один раз
├── OPEN.md            ← единый реестр нерешённых вопросов
├── roadmap.md         ← фазы и work items, статусы руками
├── product/           ← учебная модель, scope (первые контракты)
├── platform/          ← kernel и сквозные принципы
├── flows/             ← сквозные сценарии (sequenceDiagram)
└── modules/           ← спеки модулей, 1 файл = модуль
    └── _TEMPLATE.md   ← обязательная структура спеки

staging/
├── README.md          ← правила staging
└── journal/           ← саммари сессий, append-only
```
