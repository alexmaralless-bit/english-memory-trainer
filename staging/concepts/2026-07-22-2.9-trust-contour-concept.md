# 2.9 mini-concept: trust contour prerequisites

Date: 2026-07-22  
Status: owner decisions required; no runtime or canon changes applied

## Finding

The target specs define the desired outputs but not an implementable source of
truth for either half of 2.9.

1. `adapters` currently adapts and compares Agent Skill files. There is no
   provider-message ingress boundary in the engine. Consequently there is no
   operation at which `provider_message_id`, user content, its hash and a span
   can be captured.
2. `audit.obligations(session_id)` must close obligations from observed CLI
   calls and domain effects. The application persists domain events, but it
   does not persist Command envelopes or CLI invocation/refusal facts. A
   forbidden action rejected before a domain event is therefore invisible.
3. Scoring §5 names three obligation families and a default ten-session window,
   but the required versioned obligations registry has no payload, policy kind,
   version selection rule, matching predicates, denominator rule, or treatment
   of incomplete history.
4. `SKILL_STARTED` / `SKILL_COMPLETED` / `SKILL_FAILED` are named but deliberately
   have no reporting channel. That is correct today, but it means the required
   self-report/effect discrepancy cannot yet be observed.

Implementing a score from successful domain events alone would silently count
only actions the engine accepted, miss forbidden attempts and invent the
registry. It would produce a plausible but false compliance score, contrary to
audit §4 and scoring §5.

## Decisions required

### PD-1 — user-turn retention and span identity

Choose whether the event stores:

- A. full raw user text plus `sha256` and a UTF-8 byte span (recommended for the
  local personal tool; independently auditable), or
- B. only provider id/hash/span with raw text retained outside the engine
  (smaller event log, but the span cannot be verified after provider retention
  expires).

Also define whether the span is always the whole message or may identify a
subspan, and whether `provider_message_id` uniqueness is provider-global or
scoped by `(provider, session_id)`.

### PD-2 — ingress owner and idempotency

Recommended: adapters owns a mutating `capture_user_turn` API invoked by the
provider bridge before any learner-facing command. It emits one untrusted
capture fact, deduplicated by `(provider, provider_message_id)`, and correlates
it to the session. The exact event name, command envelope and behavior for the
same id with different content must be accepted before implementation.

### PD-3 — authoritative CLI observation

Options:

- A. persist every CLI Command and its terminal result/refusal as append-only
  facts in the event table (recommended; one audit source, rejected forbidden
  attempts remain visible);
- B. maintain a separate append-only command journal (clean separation, but
  audit §4 currently says the event table is authoritative and would require a
  canon change);
- C. infer calls from domain effects (rejected: cannot observe read commands,
  refusals or forbidden attempts).

Option A needs a rule for read-only commands: recording their invocation is a
write, while cli §4.4 currently classifies diagnostics as non-mutating. The
contract must state whether audit telemetry is exempt or written by an outer
transport after the read.

### PD-4 — obligations registry payload

Approve a versioned payload defining, at minimum:

- registry id/version and measurement-window session count;
- obligation id and applicability predicate;
- required observable command/effect patterns and forbidden patterns;
- correlation scope and ordering/causation requirements;
- whether several effects close one obligation and whether one effect may close
  several obligations;
- incomplete-history and unavailable-policy behavior (`no-data`, not failure);
- how a session pins or otherwise selects the registry version.

Recommended initial obligations are the three already named by scoring §5:
required skill/version, correction protocol, and forbidden-action absence. The
numerator/denominator then follows only after applicability is deterministic.

## Implementation sequence after approval

1. Add capture/command facts with idempotency and trust labels; prove learner
   scoring never consumes them.
2. Add and activate the obligations registry through the policy lifecycle.
3. Implement read-only `audit` views over canonical event sequence, explicitly
   separating observed effects from self-reports and reporting completeness.
4. Fold Tutor Compliance over the pinned/selected registry and last N eligible
   sessions; return `no-data` when the denominator is empty.
5. Publish the three read-only audit CLI commands already specified in
   `wiki/modules/audit.md` and add deterministic replay/correlation tests.

The strict xfails in `tests/audit/test_trust_contour_contract.py` are executable
markers for the missing ingress and obligation-correlation surfaces. They must
be replaced by behavioral tests once these decisions are accepted.
