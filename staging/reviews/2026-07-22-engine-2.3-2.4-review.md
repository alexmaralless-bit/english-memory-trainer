### Finding 1 — MAJOR (latent): the scoring fold is not hermetic w.r.t. the ambient decimal context

**File:** `scoring/engine.py` — `fold_scores`, esp. the stability update `factor = _ONE + context.divide(...)` (line 238) and `growth_base - _ONE` (line 238), the mastery `_ONE - hint_penalty * Decimal(hints)` (line 181), `current + delta` / `current - regression_penalty` (lines 202, 247), the cap subtractions (lines 188, 194). Same pattern in `evidence/assessment.py:405` (`numerator / total_weight`) and `scoring/aggregates.py:136-139` (`learning_score`).

**Defect.** The module docstring claims *"Every arithmetic step runs in the policy's fixed Decimal context (precision 28, ROUND_HALF_EVEN) … so two folds over the same events are byte-identical."* That is false. Only the `context.multiply/divide/create_decimal` calls use the pinned context. Bare `+`, `-`, `*` and the final `/` use `decimal.getcontext()` — the process-global thread context. So the snapshot that `trainer scoring replay` hashes depends on a mutable global the fold never controls. The determinism contract is "same events + same **pinned policy** → byte-identical"; the pinned policy pins precision 28 precisely to be context-independent, and the fold does not honor it.

Note the codebase's own inconsistency: the *read* path (`retrievability`, `due_backlog`) correctly wraps its Decimal math in `with decimal.localcontext(context):` — so the author knew the idiom but did not apply it to `fold_scores` / `learning_score` / the `finalize_attempt` aggregation.

**Reproduction** (`repro1.py`, `repro5.py`): same events, one fold under the default context, one fold inside `decimal.localcontext(Context(prec=6, rounding=ROUND_DOWN))`:

```
stability (default ctx): 18.65123132621758215761150973
stability (prec6/DOWN ): 18.6513245996187500
hash default: bc291833410fd42adb9a29d407e13efea9041db0247603cbae9c2fad11fd0395
hash altered: 59e982ccfeab90ba3732dc1b973d3895a30e2b0bdcd0cf3eabed1e630db7b4ab
HERMETIC (should be True): False
```

Contrast, same script, the read path that *is* pinned:
```
retrievability (default): 0.7408182206817178660668737793
retrievability (prec5)  : 0.7408182206817178660668737793
SAME (hermetic via localcontext)? True
```

**Why "latent" and not BLOCKER-now:** CPython's default context is already precision 28 / ROUND_HALF_EVEN, and nothing in the repo mutates the global default, so **replay within the shipped app is stable today**. This becomes a live BLOCKER the moment any dependency (or a future `decimal.setcontext`/`getcontext().prec = …` anywhere in-process, or a different platform/embedding default) changes the ambient context — which is exactly the cross-process/cross-machine independence `replay` is meant to guarantee. Also worth noting: `replay_scores` folds twice **in the same process** and compares, so it cannot catch this class of divergence — its "consistent: true" is effectively always true.

**Suggested direction (do not apply):** wrap the whole body of `fold_scores`, `learning_score`, and the `finalize_attempt` score aggregation in `with decimal.localcontext(scoring_context(policy)):` (matching what `retrievability`/`due_backlog` already do), or route every operation through explicit `context.*` calls. Then re-run the altered-context repro and confirm the hash is stable.

### Finding 2 — MAJOR: `close_review` never confirms an open-answer (rubric) review step

**File:** `evidence/reviews.py:60-71` (`_latest_assessed_attempt`) and `:105-113` (outcome computation).

**Defect.** `_latest_assessed_attempt` scans only `attempt.recorded` events whose payload `status == "assessed"`. Objective checks satisfy that (they are recorded already-assessed). But an **open answer** is recorded as `status="recorded"` and only becomes assessed later via `finalize_attempt`, which emits `attempt.state_changed` (and mutates the aggregate) — it never emits an `attempt.recorded(status=assessed)`. So for any review whose step was answered open, `_latest_assessed_attempt` returns `None`, and `close_review` yields `INSUFFICIENT_EVIDENCE(reason=not_attempted)` regardless of how strong the rubric score was. The scheduler then merely holds the interval and books a short retry, and knowledge state never advances via that review. (Secondary defect: even if it *did* locate the finalized attempt, line 110 reads `assessment.get("correct")`, a field rubric assessments do not carry — it would misclassify a strong answer as `REGRESSION`.)

**Reproduction** (`repro3.py`): a `spontaneous_production` review step, a strong open attempt finalized to `disposition=scored, score_ppm=616667, contributing=True`, then `close_review`:

```
attempt recorded status: recorded   primary_target: {...'grammar.past-simple.narrative'...}
finalize: disposition= scored  score_ppm= 616667  contributing= True

close_review outcome:  INSUFFICIENT_EVIDENCE   reason: not_attempted
Expected (given a scored, strong rubric finalize): CONFIRMED
```

**Impact:** every open-modality review (writing / spontaneous / transfer — the bulk of the text-production scope) can never CONFIRM, so its spaced-repetition interval never advances and the topic never re-consolidates through review. Objective-check reviews are unaffected.

**Suggested direction (do not apply):** compute the review outcome from the finalized assessment (the assessed attempt aggregate or the `attempt.state_changed` fact for the step), mapping `disposition/score_ppm` (against the mastery criteria) to CONFIRMED / REGRESSION / INSUFFICIENT_EVIDENCE, rather than looking up a non-existent `attempt.recorded(assessed)` + `correct` for the open path.

### Finding 3 — MINOR: XP fold misses every rubric-finalized attempt

**File:** `scoring/aggregates.py:155-166` (`xp_ledger` keys `attempt.recorded` with `status=="assessed"`) vs `evidence/assessment.py:438-457` (`finalize_attempt` emits `attempt.state_changed`, never `attempt.recorded(assessed)`).

**Defect.** The `xp_ledger` docstring promises XP for "finalized (assessed) attempts." Objective attempts are recorded already-assessed and do earn XP; a rubric attempt is finalized via `attempt.state_changed` and earns nothing. So the award source is inconsistent across the two assessment paths, and the whole rubric path is invisible to XP.

**Reproduction** (`repro2.py`): a conversation attempt finalized to `disposition=scored, score_ppm=616667`:
```
xp total BEFORE finalize: 0   AFTER finalize: 0
attempt.recorded(status=assessed) events: 0
attempt.state_changed events: 1
=> the finalized assessed attempt awarded 0 XP.
```

XP is a soft gamification metric (not learner state, not scoring), hence MINOR — but it is a real "wrong number under a real path." Suggested direction: have `xp_ledger` also recognise the rubric finalization fact (e.g. `attempt.state_changed → assessed`), award-once by `attempt_id`, keeping the objective and rubric paths mutually exclusive so no attempt is double-counted.

### Finding 4 — MINOR (debatable): schedule-derived memory pages declare `source: operational`

**File:** `memory/engine.py:215` (reviews), `:258` (next-session), `:273` (vocabulary-review).

These pages are built from `fold_schedules(store, …)`, which is a pure fold over the event log — i.e. event-sourced, replayable state, **not** SQLite-authoritative operational state. Canon 5 (per the module docstring) splits `source` into "event-sourced learning state" vs "SQLite-authoritative operational state"; labeling schedule projections `operational` puts them on the wrong side of that split. (Session/plan pages, which *are* SQLite aggregates, are correctly `operational`; topic/lexicon/current-level are correctly `event-sourced`.) This is metadata only — bytes stay deterministic and drift-checkable — and one could defend "operational" as the *domain* role of a schedule, so I rank it MINOR/debatable rather than a hard defect.
