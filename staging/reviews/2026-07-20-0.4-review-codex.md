# Red-team ревью 0.4: Evidence, Scoring & Review

Дата: 2026-07-20  
Предмет: `wiki/modules/evidence.md`, `wiki/modules/scoring.md`, `wiki/modules/scheduler.md` (commit `5da669e`) и их стыки с принятым каноном.  
Метод: только документы; фактов о коде нет. Принятые `[PD-2026-07-20]` (две оси, целые CEFR bands, Learning Score) не оспариваются.

## Резюме: топ-5

1. **BLOCKER — 0.4 не даёт schema `Topic.mastery_criteria`, но roadmap объявляет П.2 разблокированной именно этой schema.** Есть только требование существования criteria и отдельный LexicalMasteryProfile; автор программы не может создать валидный criteria object для Topic.
2. **BLOCKER — clock-trigger `overdue → AT_RISK` не имеет event/replay protocol.** `review_status` operational, событие перехода не объявлено, а replay нельзя честно зависеть от текущего wall-clock. AT_RISK может различаться при одном event log.
3. **MAJOR — покрытие CEFR per core skill невычислимо: Topic не имеет core-skill mapping, а Track не эквивалентен Grammar/Vocabulary/Reading/Writing.**
4. **MAJOR — placement ceiling `ACTIVE`, никогда `MASTERED`, не реализован в scoring.** Обычный `CONFIRMED` из ACTIVE может перевести placement target в MASTERED.
5. **MAJOR — semantic identity/multi-credit и scheduler outcomes объявлены закрытыми, но правила остаются словами.** Не определены allocation одного span и ветка `INSUFFICIENT_EVIDENCE` для interval schedule.

## Находки

### 0.4-1. Topic mastery-criteria schema отсутствует — BLOCKER

**Файл и раздел → точная цитата:** `wiki/modules/curriculum.md`, §2: «`mastery_criteria` — по versioned schema контракта 0.4»; §5: validator ловит «отсутствие `mastery_criteria` … на required dimension»; `wiki/modules/scoring.md`, §6 описывает только «у каждого **LexicalItem** versioned `LexicalMasteryProfile`», а §3 употребляет «mastery-критериях» без структуры; `wiki/roadmap.md`, строка П.2: «0.4 готов (**mastery_criteria schema есть**)».

**Почему дефект:** 0.4 не определяет ни форму, ни обязательные поля, ни version selector, ни relation Topic criteria ↔ required dimensions. Lexical profile не является Topic schema. Поэтому П.2 не может создать проверяемые topics, а curriculum validator не имеет канонической нормы. Это прямое расхождение roadmap/curriculum/0.4 и блокирует следующий заявленный work item.

**Предлагаемая правка:** в 0.4 добавить versioned schema для `Topic.mastery_criteria` (per required dimension, type/fields, policy/version reference, validation rules и связь с transition table) либо честно вернуть schema в OPEN с владельцем 0.4 и восстановить зависимость П.2.

### 0.4-2. Overdue→AT_RISK не становится replayable фактом — BLOCKER

**Файл и раздел → точная цитата:** `wiki/modules/scheduler.md`, §2: «Review_status … **operational**, управляется часами»; §4: «просрочка … переводит knowledge state в `AT_RISK` по versioned policy»; §7 publishes: только `REVIEW_SCHEDULED`, `REVIEW_DUE`, `RE_ENTRY_RECOMMENDED`; `wiki/modules/scoring.md`, §1: scoring «детерминирован и версионируем», §3: AT_RISK вход допускает overdue; `wiki/platform/foundation.md`, §2: knowledge state event-sourced и replay reconstructs it from event store.

**Почему дефект:** переход knowledge state — event-sourced learning fact, но его trigger — current operational clock/status. Не задано событие threshold crossing, его `occurred_at`, `next_review_at`, pinned scheduler policy и команда/reducer, которая эмитит `STATE_TRANSITION`. Replay либо читает не-rebuildable schedule, либо заново сравнивает с current time — оба пути не дают одинаковый historical state.

**Предлагаемая правка:** scheduler при crossing append-only эмитит факт наподобие `OVERDUE_AT_RISK_TRIGGERED` с target, boundary timestamps и pinned policy; scoring атомарно применяет/публикует state transition. Replay применяет этот факт, а не текущий clock. Добавить crash/idempotency semantics для повторной scheduler sweep.

### 0.4-3. Per-skill CEFR coverage не имеет map Topic → core skill — MAJOR

**Файл и раздел → точная цитата:** `wiki/modules/scoring.md`, §4: «Per-skill (Grammar/Vocabulary/Reading/Writing) CEFR = … coverage: ≥ `min_topics` независимых тем band'а»; `wiki/modules/curriculum.md`, §2 Topic-format содержит `cefr`, `track`, `module`, `dimensions`, но не core skill; `wiki/glossary.md`: core skills — Grammar, Vocabulary, Reading, Writing.

**Почему дефект:** Topic может относиться к Written Interaction, Written Production, US Tech English или Everyday track; нет нормативного rule, какие из них и с каким весом засчитываются в Writing/Grammar/Vocabulary. Track не равен core skill. Две реализации посчитают coverage одной и той же программы по-разному; unknown-as-unknown не спасает от отсутствия domain membership.

**Предлагаемая правка:** добавить в 0.4 versioned core-skill contribution map (на Topic/track/dimension, с multipliers/cap и dedup) либо обязательное `core_skill_contributions` в Topic schema. Owner — 0.4; это не content P.2.

### 0.4-4. Placement ceiling не энфорсится scoring-моделью — MAJOR

**Файл и раздел → точная цитата:** `wiki/product/learning-model.md`, §6: «placement … максимум `ACTIVE`, **никогда `MASTERED`**»; `wiki/flows/placement.md`: «placement submit … evidence проверенным темам/LexicalItem»; `wiki/modules/scoring.md`, §3: `ACTIVE + CONFIRMED → MASTERED²` при criteria + retention.

**Почему дефект:** Evidence несёт `mode`, но scoring не задаёт placement mode/cap. Placement evidence идёт обычным путём и при ACTIVE target может вызвать `CONFIRMED`/MASTERED. Не определено также, как короткий rubric-writing остаётся provisional и не повышает полный Writing CEFR. Это нарушает принятый ceiling именно на механизме, который им владеет.

**Предлагаемая правка:** в scoring policy добавить immutable evidence origin `placement`, максимальный state `ACTIVE`, и отдельный rule для rubric-writing/provisional per-skill level; закрепить capture origin в evidence event и покрыть replay test.

### 0.4-5. Multi-credit allocation и статус непроверяемой observation не определены — MAJOR

**Файл и раздел → точная цитата:** `wiki/modules/evidence.md`, §4.1: «один span … распределяется по **явному правилу**»; там же observation «отклоняется **или помечается**»; §7 объявляет OPEN-7 закрытым на уровне правил.

**Почему дефект:** «явное правило» не является rule: не сказано, делится ли credit, выбирается primary target, применяется ли cap, как фиксируется allocation в event. «Помечается» не говорит, участвует ли observation/evidence в scoring. Эти развилки меняют Mastery, CEFR, XP и replay; OPEN-7 нельзя считать закрытым при двух допустимых поведениях.

**Предлагаемая правка:** зафиксировать allocation record в evidence event (target/dimension/contribution/used-or-rejected reason) и deterministic algorithm; для unverified observation определить `reject` либо non-contributing audit status. Численные weights могут остаться tunable, но ветка и инвариант должны быть единственными.

### 0.4-6. Таблица переходов не тотальна: `NEW × RECOVERED = —` — MAJOR

**Файл и раздел → точная цитата:** `wiki/modules/scoring.md`, §3: в строке `NEW`, столбце `RECOVERED` стоит «`—`»; ниже: «тотальность гарантирована (каждая пара определена, INSUFFICIENT_EVIDENCE — обычно no-op)»; `wiki/product/learning-model.md`, §4: «для каждой пары `(knowledge state, review outcome)` определён исход, включая no-op».

**Почему дефект:** символ «—» не определяет ни no-op, ни invalid outcome, ни stable error. Если corrupted/late evidence или correction даёт `RECOVERED` для NEW, reducers расходятся. Это прямое нарушение обязательной total transition table, которую OPEN-10 теперь называет закрытой в 0.4.

**Предлагаемая правка:** заменить «—» на явно выбранный result (`NEW` no-op либо stable domain error, с correction semantics) и описать event/replay behaviour для invalid outcome-state pairs.

### 0.4-7. Scheduler не определяет `INSUFFICIENT_EVIDENCE` и tie-break выдачи целей — MAJOR

**Файл и раздел → точная цитата:** `wiki/modules/scheduler.md`, §3 перечисляет только CONFIRMED/RECOVERED, REGRESSION и PROGRESS; `wiki/glossary.md` содержит пятый ReviewOutcome `INSUFFICIENT_EVIDENCE`; scheduler §5 задаёт приоритет «по Retrievability, просрочке, слабым dimensions, prerequisites …».

**Почему дефект:** after abandoned/insufficient review неизвестно, сохраняется ли interval, назначается ли retry и когда. Это меняет next review и state `due`. Также критерии priority не задают total order: одинаковые values в SQLite/query order дадут разный Session Manifest, против детерминизма kernel. Обе нормы влияют на production behaviour, не только на calibration.

**Предлагаемая правка:** добавить branch для `INSUFFICIENT_EVIDENCE` (например hold/retry policy, versioned) и canonical priority tuple с stable tie-breaker (`target_id`/sequence). Проверить replay и identical due list при equal priorities.

### 0.4-8. Numeric determinism заявлен, но `exp` и initial Stability не заданы единственно — MAJOR

**Файл и раздел → точная цитата:** `wiki/modules/scoring.md`, §2.1: «fixed-precision decimal с документированным rounding»; §2.2: `Retrievability(t) = exp(…)` и «начальная Stability … дефолт **1–3 дня**».

**Почему дефект:** `exp` для decimal требует алгоритм/precision/rounding mode; их в 0.4 нет. «1–3» — диапазон, а не default. Две scoring-policy implementations, обе следуя тексту, получат разные Retrievability/intervals. Ссылка на future calibration не устраняет replay: pinned policy должна содержать однозначные values и numeric context уже сейчас.

**Предлагаемая правка:** определить exact Decimal context, exp approximation/version and rounding points, и один initial-Stability default (либо mandatory concrete policy parameter). Параметры можно калибровать, но каждая versioned policy должна быть total и executable.

### 0.4-9. XP и Tutor Compliance заявлены закрытыми, но не имеют вычислимой схемы — MAJOR

**Файл и раздел → точная цитата:** `wiki/modules/scoring.md`, §7: «База за практику … + множители …; daily cap. … eligibility для ABANDONED **определена**»; §5: Tutor Compliance — «доля соблюдённых обязательств агента за недавние сессии»; `wiki/product/learning-model.md`, §8 требует award-once source ID, units, eligibility в т.ч. ABANDONED, caps и immutable `practice_day`/day dedup.

**Почему дефект:** не перечислены awardable source event types, units, ABANDONED eligibility, daily cap key/day dedup, window/denominator Tutor Compliance и raw audit inputs. «Определена» не соответствует тексту. Это допускает XP award за один источник дважды через разные categories, расходящийся streak и произвольный compliance score, при том что OPEN-12 помечен закрытым.

**Предлагаемая правка:** задать immutable award schema (`source_id`, award kind, `practice_day`, amount/policy), mutually exclusive eligibility и cap/dedup order; для compliance — measurement window, obligations registry, event evidence, denominator/no-data rule. Numeric amounts остаются policy values.

### 0.4-10. `contribution_scope` имеет неясную cardinality и расходится с multi-credit cap — MINOR

**Файл и раздел → точная цитата:** `wiki/modules/evidence.md`, §2: Evidence имеет поле `contribution_scope`; §4.4: «каждое evidence помечено `contribution_scope` (informal-профиль / writing / transfer / core-CEFR)»; там же: informal production «даёт компонент writing/transfer с dedup и cap».

**Почему дефект:** поле названо единичным scope, но production может одновременно дать writing и transfer, а cap относится к пересечению informal/CEFR. Без enum vs set и allocation record impossible to know whether evidence is valid and how it contributes. Это частный случай 0.4-5, но важен для API/schema.

**Предлагаемая правка:** определить cardinality (`set` or one primary plus contributions[]), допустимые combinations и per-scope cap allocation in event payload.

### 0.4-11. Роль self-report в measured vs provisional working level не определена — QUESTION

**Файл и раздел → точная цитата:** `wiki/modules/scoring.md`, §4 одновременно определяет «Per-skill CEFR = … coverage» и что self-report «даёт provisional working estimate»; `wiki/platform/foundation.md`, §2.2: self-report влияет на provisional working estimate/briefing/recommendations, не scoring.

**Почему дефект:** не указан returned/displayed field и precedence, когда одна часть skills measured, а другая self-reported. Это может быть продуктовой развилкой, но сейчас влияет на Learning Score «current working level» и recommendations.

**Предлагаемая правка:** выбрать и назвать отдельно `measured_working_level` и `provisional_working_estimate`, plus rules for mixed skills; Learning Score/recommendations consume explicit field. Оформить PD или OPEN, не выбирать молча в implementation.

## Полнота OPEN / roadmap — НАХОДКИ

### 0.4-12. Новые незакрытые механизмы не зарегистрированы, а 0.4 объявлена done-with-open — MAJOR

**Файл и раздел → точная цитата:** `wiki/OPEN.md` называет OPEN-1/7/8/10(table)/12/13/18 закрытыми; `wiki/roadmap.md`: «0.4 … **done-with-open** … закрыл OPEN-1/7/8/12/13/18 (модель)».

**Почему дефект:** находки 0.4-1…0.4-9 — не калибровка констант, а отсутствующие schemas, event protocol и total branches. У них нет OPEN, owner/acceptance criteria и зависимости. В частности, P.2 ошибочно разблокирована при отсутствии Topic criteria schema; 0.5 получит незафиксированный moment/outcome scheduler contract.

**Предлагаемая правка:** завести/расширить OPEN с owner 0.4 для Topic criteria schema, time-trigger event, CEFR map, placement cap, evidence allocation, scheduler branches/tie-break, XP/compliance, numeric context; вернуть соответствующие зависимости roadmap до закрытия.

## Проверено, ок

- Agent передаёт observations/raw answer, а не готовую review classification; engine — единственный scorer.
- Разделение AttemptAssessment и terminal ReviewOutcome, semantic source-span identity и capture-into-event заданы в правильной owner-зоне 0.4.
- Safety-overlay не переписан: production eligibility остаётся active-policy вопросом П.3/0.5, а historical scoring — pinned.
- Mastery отделена от Stability/Retrievability; due/overdue остаётся review-status, не knowledge state; backlog не становится lock.
- Вынесение FSRS за scheduler interface и целые CEFR bands не противоречат принятому канону.

## Вердикт

**FAIL** — есть два BLOCKER: отсутствует Topic `mastery_criteria` schema, заявленная как разблокирующая П.2, и не определён replayable event protocol для time-driven `overdue → AT_RISK`.
